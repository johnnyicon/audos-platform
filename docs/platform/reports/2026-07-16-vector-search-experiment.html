Can DoKnow actually search its own content?

Two rounds of live testing against the real Audos platform, to answer one question before committing to an architecture: when DoKnow builds a course from your own uploaded material, can it actually find the right pieces of that material — on this platform, as it exists today?
2026-07-14 → 2026-07-16 · 12 tests, 3 rounds Resolved — pipeline stays on Audos
00 The short answer

No, Audos doesn't have a dedicated semantic-search database — but it can produce and compare real embeddings today, through a path we almost missed. There's still no vector column type; pgvector sits on their server, present but switched off, only Audos's own engineers can turn it on. That part never changed. What changed is everything downstream of it: a real embedding is one authenticated call away via an undocumented gateway (platform.integrations.proxy), and comparing embeddings at real size costs single-digit milliseconds at DoKnow's scale.

This report went through three drafts of "the answer," and the middle one was wrong twice. Round 2 said the search question was settled; it wasn't (the vectors were fake). Round 3's first pass said no embedding capability existed at all; that was also wrong — it asked the platform about a feature by guessing feature-shaped names, instead of asking what the platform actually has. See §06 for both corrections, told straight.

01 What we were actually trying to do

DoKnow's core idea: you hand it a pile of your own content — videos, PDFs, articles you saved — on a topic. Instead of the AI just making up a course from its general knowledge, it builds one from your actual material. For that to work, the system has to be able to find the right piece of your content when it's writing each lesson — the three minutes of a video that actually cover "choosing a hive location," not a guess.

The standard way modern AI systems do this is called semantic search. Every piece of your content gets converted into a long list of numbers — an "embedding," a kind of fingerprint of what it means, not just what words it uses. Your question gets the same treatment. Then the system looks for the stored fingerprints that are mathematically closest to your question's fingerprint.

The fast way

A proper database index for embeddings is like a library catalog — it can jump almost straight to the closest matches without checking every book, even in a library with millions of books.

The way we tested

Without that catalog, you check every single book yourself, one at a time, and keep the closest match. Slower in theory — but if your library is one course's worth of material, not millions of books, "slower" can still be instant.

Round 1 found the library catalog isn't available to us. Round 2 asked: does that actually matter, at the size of library DoKnow really has?

02 The hypothesis
Stated before testing

If Audos cannot support fast content search and reliable delayed/background processing, DoKnow's content pipeline (upload → transcribe → search → generate) should be built as a separate service outside Audos, rather than entirely on the platform.

Two platform capabilities would decide it: whether embeddings can be searched fast enough without the missing catalog, and whether slow, multi-step work (transcribing a video, say) can run without the user's browser staying open the whole time.

03 Round 1 — five baseline tests

Five direct questions against the live platform, each one a real server-side script written and run for this test, not a claim taken from documentation.

1Vector storage

Try to create a database column built for storing an embedding.

Rejected. The library-catalog tool (pgvector) is present on the server but not switched on for us, and we have no way to switch it on ourselves.

2Calling outside services

Can DoKnow's own code call an external service — a transcription API, an embedding API — from inside Audos?

Yes, freely, no restrictions found.

3File upload

Upload a real file (like a source PDF) and find the actual size limit.

Works, capped at just under 50 MB per file.

4Scheduled / background work

Set something to run automatically later, the way you'd process a big upload without making the user wait.

Created successfully, but never actually ran — checked 2+ hours after it was due, still hadn't fired.

5Built-in AI writing

Does Audos have its own AI text-generation available to call directly?

Yes, works, real responses.

Two findings — #1 and #4 — looked like they'd rule out building the content pipeline on Audos at all. Before writing that up formally, we went back to close the gaps in exactly those two findings.

04 Round 2 — closing the gaps

Four follow-up tests, aimed specifically at the two findings that mattered most.

AIs "no catalog" actually slow, at our size?

Store 50, then 300, then 1,000 fake embeddings, and time how long a full one-by-one comparison actually takes — never measured in round 1, just assumed to be a problem.

Sub-millisecond at every size tested — 0.02 ms at 50 rows, 0.12 ms at 300, 0.28 ms at 1,000. A single DoKnow course realistically has tens to a few hundred chunks of content — well inside the range we just measured as instant. Caveat: these were fake, 5-digit placeholder vectors, not real embeddings (typically 384–1,536+ digits) — the comparison math costs the same regardless of what the numbers mean, so row-count scaling is genuinely proven, but this alone doesn't prove real semantic search works, and dimensionality at real size was never directly measured.

BIs there any other useful tool available?

Round 1 only checked for the one specific catalog tool. Pull the complete list of everything available.

70 tools available total; only one (a basic scripting tool, unrelated to search) is actually switched on. The embedding catalog tool is there, unswitched, exactly as round 1 found — plus a second, newer version of the same kind of tool, also unswitched, that round 1 didn't know to look for.

CRetest the scheduled/background work

Same test as round 1's #4, run again with a different timing setting, plus asking Audos's own assistant directly whether this is a known problem.

This time it fired — on time, within 9 seconds of when it was due. The exact opposite of round 1's result, on the same platform. Audos's own assistant, asked directly, said plainly it has no record either way of whether this is a known issue.

DDoes DoKnow itself have to wait for the schedule?

Instead of trusting the automatic scheduler, what if DoKnow's own app just does the waiting — calling the server five times in a row, one piece of a job at a time?

5 out of 5 succeeded, no slowdowns, no blocks, no login issues between calls — about a second and a half each.

06 Round 3 — closing both gaps, and catching our own mistake

Round 3 ran two tests. The first re-measured the search benchmark with real 1,536-number vectors (OpenAI's actual embedding size) instead of the 5-number placeholders round 2 used. The math scaled exactly the way arithmetic says it should — roughly 300x more work per comparison — and it still didn't matter: about 0.003ms per row at 300–1,000 rows, a full 1,000-row scan in one to three milliseconds. The real cost was always fetching rows from the database, never comparing them once fetched. That question is closed.

The second test is the one worth slowing down for, because we got it wrong first and the wrong answer is the more useful story. We asked the platform's own runtime whether anything named openai-embeddings, vector-search, or pinecone existed. Nothing did — every guess came back false. We wrote that up as "no embedding capability exists," and for about an hour, that's what this report said.

It was wrong. We'd asked about a feature by guessing feature-shaped names, instead of asking what the platform actually has. What it has is a generic proxy — platform.integrations.proxy(providerName, path, options) — that forwards an authenticated request to a small allowlist of real providers: OpenAI, Stripe, Twilio, Heygen. The bare name openai is enough. Point it at /v1/embeddings with a model and some text, and it returns a real, 1,536-number embedding — using Audos's own API key, not ours.

The lesson isn't just "Audos has more than it documents." It's that a negative capability test can be wrong about the platform when it's really only wrong about the names it tried. We caught this one because two overlapping round-3 tests contradicted each other — not a process to depend on going forward, but worth writing down as its own finding.

07 What this means, plainly

All three questions this report opened with are now resolved. The scheduler is unreliable but doesn't matter — the app can pace its own background work, proven 5/5. Comparing embeddings at DoKnow's real scale, at real embedding size, costs single-digit milliseconds. And a real embedding is one authenticated proxy call away, with Audos supplying the API key.

None of that was true when this report first published. Getting here took two corrections, both told in place rather than quietly overwritten: round 2's fake-vector overclaim, and round 3's own guessed-names false negative. Both are left visible above, not smoothed over — the mistakes are as much a finding about this platform as the final answer is.

Background processing
Stays on Audos
  • The app paces its own slow, multi-step work by calling a hook repeatedly — proven reliable, 5/5, no friction
  • Doesn't depend on the platform's own scheduler, whose reliability is still unexplained
→
Content search
Stays on Audos
  • Embeddings generated via platform.integrations.proxy('openai', '/v1/embeddings', ...) — no API key of our own
  • Stored as JSON, compared brute-force — proven fast at real row counts and real embedding size

Still worth formally asking Audos for: documentation of platform.integrations and proxy(), since it's currently discoverable only by introspecting the runtime and guessing the right call shape. Native vector/vectorscale column support is still worth requesting for headroom well past DoKnow's current scale. Neither is a reason to wait — the ingestion pipeline has no remaining architectural reason to live anywhere but Audos.
