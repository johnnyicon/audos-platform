# SDK blog hosting: Cloudflare Worker + Static Assets + Basic Auth

*Written 2026-07-22. Not an Audos-platform finding — this is infrastructure for the SDK blog itself,
kept here per the "durable, generic, worth finding later" bar in `24-where-new-findings-go.md`, since
the caching gotcha below is a real, non-obvious platform lesson (about Cloudflare, not Audos) that would
otherwise get relearned the hard way.*

## What's running

The SDK build-log blog (`blog/dist/index.html`, generated by `scripts/build_blog.py`) is deployed as a
Cloudflare Worker with a Static Assets binding, gated by HTTP Basic Auth. Source lives in
`blog/cf-worker/`:

```
blog/cf-worker/
  wrangler.toml       # run_worker_first = true — see gotcha below
  src/worker.js        # Basic Auth check, then serves the asset
  public/index.html    # copy of blog/dist/index.html, synced on each deploy
  redeploy.sh           # rebuild + redeploy in one step
```

Live at **`https://audos.merkhetventures.com`** (canonical) — the original
`audos-sdk-blog.sowgood.workers.dev` `workers.dev` URL still resolves too (same Worker), but isn't
advertised. Hosted on the **Merkhet Ventures** Cloudflare account
(`accountId 0885e517f929a358204d791ac76dbb08`) — not Tahua, not any other account tied to this machine.

## History: bathala.io → merkhetventures.com

The real goal was always `merkhetventures.com` — the account this project actually belongs to — but it
wasn't reachable on day one of this setup (2026-07-22). Two things blocked it at the time:

1. **`merkhetventures.com`'s DNS wasn't on Cloudflare yet.** It was on iwantmyname, and — critically —
   not an idle domain: MX records point at Google Workspace (real, live email) and the root A records
   point at GitHub Pages (a real, live site). Moving it wholesale (every record, not just a new
   subdomain) carried real risk to live email if anything wasn't replicated correctly first — not
   something to do casually for an internal blog.
2. **The lower-risk alternative — Cloudflare's "Subdomain setup"** (delegate just a subdomain to its own
   Cloudflare zone via one NS record, leaving the root domain's email/site completely untouched) —
   **turned out to be Enterprise-plan only.** Checked the account directly:
   `enterprise_zone_quota.maximum: 0`. Real, non-obvious platform-knowledge gap: Cloudflare's own
   zone-setup comparison table lists Subdomain setup and CNAME (Partial) setup as unavailable on
   Free/Pro/Business — only Full setup (the whole domain) works below Enterprise. Don't assume
   "Cloudflare supports X" transfers to "this account can do X" without checking plan-gating.

With both closed off, `bathala.io` (another domain already live on the same Cloudflare account) was used
as a temporary stopgap (`sdk.bathala.io`) — a real business domain, unrelated to this project, same
brand-mismatch tradeoff as the `sowgood` `workers.dev` prefix, chosen only because it had no blockers.

**Resolved 2026-07-23.** The owner transferred `merkhetventures.com`'s DNS to Cloudflare. Verified
before treating the transfer as safe to build on: pulled the new zone's imported DNS records directly
and confirmed all 5 Google Workspace MX records, all 4 GitHub Pages A records, the Google Workspace
CNAMEs, and the XMPP SRV records all came through intact — checked before the nameserver cutover was
even live, not after. (No DKIM record exists for this domain at all, at Cloudflare or previously at
iwantmyname — not a migration gap, just never configured.) Once the zone hit `status: active` (took a
couple minutes after the nameserver switch propagated) and its TLS cert activated, attached
`audos.merkhetventures.com` as the Worker's Custom Domain, declared it in `wrangler.toml`, and
redeployed — which automatically detached the `sdk.bathala.io` Custom Domain in the same step (`bathala.io`
itself, unrelated to this Worker, confirmed unaffected). Verified with repeated 401/401/200 checks on
the new URL before calling it done.

Credentials (HTTP Basic Auth, stored as Worker secrets, not in source):
```
wrangler secret put BASIC_AUTH_USER   # currently: team
wrangler secret put BASIC_AUTH_PASS   # currently: audos
```

To redeploy after editing blog content: `blog/cf-worker/redeploy.sh`.

## Why not a native "password protect my site" toggle

Checked before building this: none of Vercel, Netlify, or Cloudflare Pages has a truly free, built-in
shared-password gate for a production domain. Vercel's native Deployment Protection requires Pro
($20/user/month). Cloudflare Access is free up to 50 users but is identity/email-based (OTP-style),
not a fixed shared username+password — and given how much of this project's own findings are about
Audos's OTP-style EmailGate causing problems, adding another email-gate here would be an odd choice.
A hand-rolled Basic Auth check in a Worker/Edge Function is the actual free path on any of the three;
Cloudflare was chosen because the account was already connected in-session, avoiding the account/team
mixup that happened on the first attempt with Vercel (see below).

## Housekeeping: temporary API tokens not yet revoked

Two narrowly-scoped Cloudflare API tokens (`temp-wrangler-deploy-audos-sdk-blog`,
`temp-subdomain-zone-setup` — Workers Scripts / Zone / DNS write, this account only, nothing else)
were created during setup to work around the MCP connector's own auth lacking token-management and
zone-create permissions. Neither could be revoked programmatically — the MCP connector's token doesn't
have permission to list or delete *other* tokens, and the temp tokens themselves aren't allowed to
revoke themselves. Low risk (scoped to Workers/Zone/DNS on this one account only), but should be
revoked by hand at `dash.cloudflare.com/profile/api-tokens` when convenient. (The later
`merkhetventures.com` Custom Domain attach didn't need a new token — the MCP connector's own default
auth was sufficient for that specific call, unlike zone creation and token management.)

## Three real mistakes made building this, worth keeping in the record

**1. Vercel login landed on the wrong account.** Running `vercel login` triggered a device-auth flow
that auto-approved via an already-logged-in browser session — for a Tahua business account, not the
account this project belongs under. That account also had a server-side default team preference
pointing every fresh `vercel link` into the Tahua team, invisible from local CLI config alone (it's
set on the account via `defaultTeamId`, not `~/.vercel/config.json`). Caught before deploying anything
into it; switched to Cloudflare instead, where the account was already correctly scoped. Lesson: when
a CLI login "just works" without visibly prompting for credentials, verify *which* account it landed on
before treating that as your working scope — don't assume the obvious one.

**2. The first working-looking deploy silently leaked content to unauthenticated requests.**
Cloudflare Workers with a Static Assets binding, by default, let requests that match a static asset
path bypass the Worker script entirely — the auth check in `fetch()` never runs for those requests
unless `run_worker_first = true` is set in `[assets]`. Initial testing looked like it worked (some
curl calls got 401), but that was propagation-delay noise; repeated testing showed unauthenticated
requests intermittently getting 200s. Root cause: assets *and* the worker's own responses were being
cached at Cloudflare's edge keyed by URL alone, ignoring the `Authorization` header — so an
authenticated request's response could get served back to a later *unauthenticated* request for the
same URL. Fixed two things together: `run_worker_first = true` (forces every request through the
auth check first) and `Cache-Control: private, no-store` set explicitly on every response the Worker
returns (stops the edge — and any downstream cache — from storing and replaying it regardless of who
asked). Verified with five consecutive rounds of no-auth/wrong-creds/correct-creds requests before
trusting it, not a single check.

**3. Proposed the Enterprise-only "Subdomain setup" as the plan without checking plan-gating first.**
Confirmed the feature exists and is real (`docs/platform/27`'s own research above), then recommended it
to the account owner before checking whether *this* account could actually use it. Only surfaced when
the zone-create API call itself rejected the request — should have checked `enterprise_zone_quota`
before proposing the plan, not after building toward it.

All three mistakes were caught before being reported as "done" — consistent with this project's own
standing rule about not trusting a first green result. Worth noting the second one specifically: a
"looks deployed, spot-checked once, moved on" verification would have shipped a gate that doesn't
actually gate anything under real traffic patterns.
