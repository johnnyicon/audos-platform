# Building it right the first time

Everything in the last two entries was a retrofit. Find the bug on a real app, diagnose it, fix it,
verify it. That works, but it leaves one question open: was all of that necessary because the platform
genuinely can't be told upfront, or because nobody had told it upfront yet?

So we ran the test directly. A brand-new, small, throwaway app — "One Good Thing," a tiny feed where you
log one good deed a day — built from a brief that stated everything we'd learned, before a single line
of code existed: land full-screen from the start, resolve any deep-link state synchronously instead of
defaulting to the old shell and correcting after paint, `JSON.stringify` every JSON column before it
ever touches the database, and if there's a way back to chat, make it a small popup, never a full
teardown of the screen.

We didn't take the completion report's word for any of it, on principle by this point. Checked by hand:
loaded the app with a screenshot fired the instant the page navigated, no delay — clean, full-screen,
no dock, no flash. Typed a real entry and logged it — no `Insert failed` error, the exact class of bug
that had shown up three separate times this week in three different pieces of code. Clicked the small
chat-access button — a compact popup opened in the corner, the app stayed exactly as it was underneath.

All four of the things we'd spent the better part of a day fixing after the fact simply weren't there to
fix. At the time, that read as: brief it upfront, and none of it happens. That's what got written here
originally.

> **Correction, added 2026-07-14.** That conclusion was only one-quarter right, and it's worth naming
> plainly rather than quietly editing it away. This app was built inside the *same* workspace as every
> other app this week — not a new one — and three of the four things being tested (the full-screen
> landing, the deep-link resolution, the chat popup) live in `Desktop.tsx`, which is shared across an
> entire workspace, not owned per app. This workspace's `Desktop.tsx` had already been fixed, days
> earlier, while retrofitting other apps. So this app inherited clean shell behavior automatically — the
> brief calling those three things out had no effect either way, because there was nothing left in the
> shared shell to get wrong. We only found this out later (see "Taking the red pill"), when a *different*
> new app, built with deliberately no special briefing at all, came out just as clean — proving the shell
> mechanics were never really being tested here, just inherited.

Only one of the four was a genuine, unconfounded test: `JSON.stringify` on every database write is
per-app code, freshly generated by whatever agent builds that specific app — not shared plumbing. Briefed
upfront, and the bug that had shown up three separate times in three other pieces of code simply didn't
happen here. That result holds.

So the real, standing finding from this entry is narrower than first stated: a data-write convention,
briefed from the start, reliably prevents its own class of bug — confirmed cleanly, no confound. Whether
the *shell* layer is equally avoidable purely by briefing, independent of any prior fix, was never
actually isolated by this experiment — testing that for real needs a workspace where `Desktop.tsx` has
never been touched, not just a new app inside one that's already been fixed. That's a distinct experiment,
genuinely not yet run, and worth running later if the question matters again.
